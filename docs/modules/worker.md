# worker

## Purpose

Background job runner: fetching retailer and Amazon prices, matching, price history. For now it loads server secrets, logs which ones are set, recovers interrupted Bright Data runs and resumes the kept ones when `DATABASE_URL` is set, builds the Amazon.com.mx source and logs which parts are configured, and exits.

## Public API

- Binary `worker` (`cargo run -p worker`).
- Environment (all optional for now; each adapter will require its own once it exists):
  - `BRIGHTDATA_API_KEY`, `BRIGHTDATA_UNLOCKER_ZONE`
  - `BRIGHTDATA_BROWSER_ZONE` (optional): Bright Data Browser API zone, only for store pages proven to need JavaScript ([ADR 0007](../decisions/0007-brightdata-browser-api.md)). Without it, Browser API fetches fail closed.
  - `RETAILER_PARSE_ALERT_THRESHOLD` (default 0.8, in 0–1) and `RETAILER_PARSE_ALERT_MIN_SAMPLES` (default 20): the parse-health alert settings (`retailers::HealthConfig`). They are read at start-up, so an invalid value stops the worker. They are logged, and the future store-fetch job owns the `ParseHealth` built from them, so a per-retailer success rate below the threshold logs a warning.
  - `SPAPI_LWA_CLIENT_ID`, `SPAPI_LWA_CLIENT_SECRET`, `SPAPI_REFRESH_TOKEN`: Amazon SP-API (LWA) credentials, read through `ServerSecrets::spapi()`. All three are needed; with only some set, the worker logs a warning naming the first missing one and uses the fallback only. How to obtain them: [amazon.md](amazon.md#owner-setup-sp-api-registration).
  - `MODEL_PROVIDER_API_KEY`
  - `DATABASE_URL` (optional for now): enables Bright Data run recovery.
- Secrets load once at start-up into `http_guard::Secret`. A variable that is set but empty, whitespace-only, contains control characters or is not UTF-8 stops start-up with an error that names the variable, never the value. The log shows only which names are set. Top-level errors pass through `http_guard::Redactor` before they are logged.
- Bright Data run recovery: with `DATABASE_URL` set, the worker connects, takes the Bright Data driver lock (`db::brightdata_runs::try_driver_lock`) and runs `brightdata::recovery::recover_interrupted`, logging how many runs were failed and kept; the lock is held until the worker exits. Still under the lock it resumes each kept dataset run with `Runner::resume_run` (default timing and caps, so one resume may poll for up to 10 minutes) and logs each outcome and a finished/active/refused/abandoned summary. Kept Amazon fallback runs (scope `amazon::FALLBACK_TENANT`/`amazon::FALLBACK_JOB`) are not resumed: their caller died with the worker, and while active they would block every new fallback lookup for up to 24 h. `resume_kept` fails them with `FALLBACK_INTERRUPTED` and, best effort, cancels their Bright Data snapshot (counted as `abandoned`). If another worker holds the lock, recovery is skipped (its runs are live). Without `DATABASE_URL`, recovery is skipped and logged. Database errors pass through `DatabaseUrl::redactor`.
- Bright Data client (`src/brightdata_resume.rs`): built from `BRIGHTDATA_API_KEY` and `BRIGHTDATA_UNLOCKER_ZONE` via `BrightDataConfig::from_secrets` (plus the optional `BRIGHTDATA_BROWSER_ZONE` via `with_browser_zone`) only when `DATABASE_URL` is set. If either is missing the log names the setting and the runner gets `transport: None`, so every resume fails the key gate (closed) without an HTTP request. Resume messages pass through `ServerSecrets::redactor`.
- Result sink: no product importer exists yet, so the worker uses `RefusingSink`, which refuses every page and record with fixed text. A downloaded run therefore stays `ready` and resumable (chosen over failing it, so the paid snapshot is not given up); it keeps its scope's active slot until a real sink imports it or it expires at a start-up more than 24 h later. Replace `RefusingSink` when the first importer lands.
- Robots pre-check: `robots_checker()` (`src/main.rs`) builds a `RobotsChecker` over the `retailers` hosts. It only applies to Unlocker runs started via `Runner::start_unlocker_run`, which skips disallowed store paths without a paid request; no worker job calls that yet (resumes via `Runner::resume_run` do not consult it, though the resume `Runner` is built with it). The future store-fetch job must build its `Runner` with `robots: robots_checker().as_ref()`, and pass `PageAccess::Browser` only for page kinds where `RetailerInfo::access_for(kind)` is `Browser`.
- Access metrics (`src/access_metrics.rs`): after recovery (and resume, if any), logs per-retailer `ok` / `blocked_needs_kyc` / `skipped_robots` / `failed` counts from `app::AccessReport::per_retailer`, built in `recover_brightdata_runs` over `db::access::PgAccessCounts` and `retailers::RetailerOfferSource::lookup_only()`; errors log a fixed warning and are swallowed.
- Binary `access_check` (`cargo run -p worker --bin access_check [--live] [--max-urls N] [--out PATH]`): checks robots.txt for the registry's sample URLs (free) and writes the dated matrix `docs/brightdata-access.md`. `--live` also fetches each allowed sample once through the channel production uses (needs `BRIGHTDATA_API_KEY` and `BRIGHTDATA_UNLOCKER_ZONE`; retries off, one request per URL, hard cap 36): page kinds where `RetailerInfo::access_for(kind)` is `Browser` (Sears MX and Sanborns categories) go through the Browser API and are marked *(Browser API)* in the matrix; everything else goes through Web Unlocker. Browser pages need the optional `BRIGHTDATA_BROWSER_ZONE`; without it they are recorded as "not checked (needs BRIGHTDATA_BROWSER_ZONE)" with no request, never sent through Unlocker. No bodies or secrets are stored.
- Binary `capture_fixtures` (`cargo run -p worker --bin capture_fixtures -- --retailer ID --kind search|product|both [--query Q] [--url URL] [--out-dir DIR] [--browser [--no-block]] [--resanitize]`): captures parser fixtures to `crates/retailers/tests/fixtures/<id>/`. It checks robots.txt first and skips disallowed pages without fetching them. It then makes one request per page (Web Unlocker, or the Browser API with `--browser`, which needs `BRIGHTDATA_BROWSER_ZONE`; `--no-block` lets that session download images, fonts and stylesheets too, to check whether blocking breaks a page, at a higher cost), country MX, retries off, hard cap 2 pages per run. Bodies pass through `retailers::fixture::sanitize` before they are written. The product URL defaults to the first offer parsed from the saved search fixture. Output is only status and size, never bodies or secrets. `--resanitize` re-sanitizes existing fixtures offline.
- Amazon source (`src/amazon_source.rs`): `amazon_source(spapi_secrets, fallback, redactor)` builds `app::FallbackAmazonSource` over `amazon::SpApiAmazonSource` (when all three SP-API secrets are set) and `amazon::BrightDataAmazonSource` (when the Bright Data client exists, `DATABASE_URL` is set and this worker holds the Bright Data driver lock; a worker without the lock logs "another worker drives Bright Data runs; Amazon fallback disabled here" and keeps SP-API only, because the lock holder's start-up recovery would fail its live runs; it uses `PgRunStore`, so the kill switch, caps and durable runs apply, scope `system` / `amazon_mx_fallback`). It only builds clients (no request) and logs `sp_api` / `bright_data` booleans, never values. No job calls the source yet. Unit tests cover "no credentials ⇒ `NotConfigured`", partial SP-API credentials and "no driver lock ⇒ no fallback".
- `PgRunStore` (`src/brightdata_store.rs`) implements `brightdata::runs::RunStore` over `db::brightdata_runs`; storage failures return fixed text and log the redacted detail. A missing settings row reads as kill switch on and connector disabled.

## Dependencies

- Workspace: `domain`, `app` (use cases and ports; the worker is a composition root), `db`, `matching`, `retailers`, `amazon`, `http-guard` (secret types and redaction), `brightdata` (run store, recovery, and the client and store handed to the Amazon fallback, [ADR 0010](../decisions/0010-amazon-spapi-lwa-brightdata-dataset-fallback.md)).
- External: `tokio`, `tracing`, `tracing-subscriber`, `anyhow`, `serde_json` (the `RunSink` record type).

## Owned tables

None directly; data access goes through `db`.
